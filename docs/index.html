Apigee → Claude Governance Gateway

A proof of concept: end-users reach Claude (Anthropic) through Apigee with no Google login, while Apigee enforces policy, meters usage, and audits every call.

Status: PoC scaffold — pre-deployment Governance: policy · usage · audit Auth wired: API key + customer-IdP JWT

The problem in one line

Apigee customers want their end-users to consume Claude services and runtimes that sit behind Apigee, without logging into anything Google (Google Workspace or the Cloud Console). Apigee stays the governance layer: policy enforcement, usage metering, and full audit. Everything is tracked, and the real Anthropic credential never leaves Apigee.

The test the design must pass: a user holding only a non-Google credential calls an Apigee endpoint and gets a Claude answer; the Anthropic key is invisible to that user; and there is a governed audit record for the call.

Cloud architecture

client / non-Google identity Apigee policy stages secrets & audit (GCP) Claude backend

The only place a Google identity can appear is the backend leg if Claude is reached via Vertex AI, and that is a hidden service identity inside Apigee, invisible to the end-user.

Identity model — how "no Google login" works

OptionEnd-user holdsApigee verifies withStatus
A. Apigee API keyAPI key tied to an Apigee Developer AppVerifyAPIKeyWIRED
C. Customer-IdP JWTJWT from the customer's own Okta / Entra / Auth0VerifyJWT (JWKS)WIRED
B. Apigee OAuth2short-lived token from Apigee's token endpointOAuthV2OPTIONAL
Both A and C are wired. The proxy does conditional auth: a request with Authorization: Bearer … is verified as a customer-IdP JWT; otherwise the x-app-key API key is verified. Both resolve a single gw.principal, so quota, metering, and audit are identical regardless of auth method. The IdP issuer/JWKS/audience come from resources/properties/idp.properties so the same bundle points at any customer IdP by config, not code.

Secret handling (the crux): the Anthropic key lives once in an encrypted KVM, is injected only on the backend leg, and never appears in any user-visible response, header, or log. End-user credentials and the backend credential are fully decoupled.

Functional

  • FR1 Non-Google credential → Apigee → valid Claude response.
  • FR2 Missing/invalid credential rejected at Apigee (401), backend never hit.
  • FR3 Anthropic key injected from secure storage; never user-visible.
  • FR4 Per-principal/tier quota; 429 on exceed.
  • FR5 Spike arrest protects backend.
  • FR6 Every call → audit record (identity, request id, model, tokens, status, ts).
  • FR7 Token usage extracted + metered.
  • FR8 Faults return clean, governed errors.

Non-functional

  • NFR1 Security — no Google login in user path; secrets only encrypted; client credential never forwarded upstream.
  • NFR2 Observability — every allow/deny/quota/cost decision queryable.
  • NFR3 Portability — backend target is a config swap, not a rewrite.
  • NFR4 Repeatability — bundle deploys from repo via script; demo reproducible.
  • NFR5 Cost control — eval tier + low token caps; no surprise spend.

In scope (PoC)

  • One Apigee proxy fronting the Claude API.
  • Non-Google end-user authentication.
  • Backend Anthropic credential held in Apigee, injected on the backend leg.
  • Governance: verify, quota, spike arrest, audit, usage metering.
  • A demonstrable call path + the audit record proving governance.

Out of scope (PoC)

  • Production multi-tenant hardening, HA, DR.
  • Billing/chargeback (usage captured, not invoiced).
  • A developer portal (Apigee provides one).
  • SSE streaming metering exactness (follow-up).
  • Claude content guardrails (this is a gateway PoC).

Acceptance / demo script

  • Valid non-Google credential → 200 + real Claude answer.
  • Invalid/missing credential → 401, backend never called.
  • Quota exceeded → 429.
  • Anthropic key absent from all user-visible output and logs.
  • Audit + usage record visible in Apigee Analytics and the external sink.

What's needed for a live deployment (dev environment)

The scaffold is complete; turning it into a running demo needs the following. None are secrets in the repo, they are provisioned into Apigee / the shell at deploy time.

NeedWhy / how
Apigee org + envAn Apigee X eval org is enough. Gives the runtime, a hostname, and Analytics. Set APIGEE_ORG / APIGEE_ENV.
gcloud + apigeecliLocal tooling to import + deploy the bundle and seed the KVM. scripts/deploy.sh uses both.
Anthropic API keyThe backend credential. Set ANTHROPIC_API_KEY; the deploy script writes it into the encrypted KVM secrets. Never committed. (For Vertex/Bedrock this becomes a service-account / SigV4 setup.)
Developer + App + API productApigee product bound to the proxy, an app under a developer → yields the API key for option A and feeds quota/analytics.
Non-Google IdP (option C)Any dev tenant — Okta / Entra / Auth0 / Keycloak. Put issuer, jwks_uri, audience in resources/properties/idp.properties; mint a test JWT.
BigQuery dataset (optional)Cloud Logging sink → BigQuery for the durable audit trail. Optional for a first demo (Analytics alone proves governance).
Decision that gates deploy: which Claude backend — Anthropic API direct (simplest, zero Google), Claude on Vertex AI (strongest story for a Google audience), or Bedrock (cross-cloud). The bundle defaults to Anthropic-direct, target designed for a one-line swap.

From zero to a governed call

  • export APIGEE_ORG=… APIGEE_ENV=eval ANTHROPIC_API_KEY=sk-ant-…
  • ./scripts/deploy.sh  (seeds KVM, imports + deploys the bundle)
  • create an API product + developer app → copy the API key
  • GATEWAY_HOST=… APP_KEY=… IDP_JWT=… ./scripts/test-call.sh
  • open Apigee Analytics → confirm the governed call + token metering

Open questions

  • Backend Claude surface — Anthropic direct vs. Vertex AI vs. Bedrock. Gates the target endpoint + backend auth.
  • Identity — lead the demo with API key (A), JWT (C), or both?
  • Audit depth — metadata only, or capture prompt/response bodies? Where does the sink live? PII / data-residency constraints?
  • Cost attribution — per-app, per-end-user, or per-tier?
  • Streaming — is SSE required for the demo?
  • Tenancy — one shared proxy or per-customer proxy/environment?

Each decision is tracked as an ADR (architecture decision record) in the decision log.
