Apigee to Claude Governance Gateway

A proof of concept: end-users reach Claude (Anthropic) through Apigee with no Google login, while Apigee enforces policy, meters usage, and audits every call.

Status: PoC scaffold, pre-deployment Governance: policy, usage, audit Auth wired: API key + customer-IdP JWT

The problem in one line

Apigee customers want their end-users to consume Claude services and runtimes that sit behind Apigee, without logging into anything Google (Google Workspace or the Cloud Console). Apigee stays the governance layer: policy enforcement, usage metering, and full audit. Everything is tracked, and the real Anthropic credential never leaves Apigee.

The test the design must pass: a user holding only a non-Google credential calls an Apigee endpoint and gets a Claude answer, the Anthropic key is invisible to that user, and there is a governed audit record for the call.

Cloud architecture

client / non-Google identity Apigee policy stages secrets and audit (GCP) Claude backend

The only place a Google identity can appear is the backend leg if Claude is reached via Vertex AI, and that is a hidden service identity inside Apigee, invisible to the end-user.

Request lifecycle

End-user / app
Sends POST /claude/v1/messages with a non-Google credential.
▼
Apigee, request PreFlow
  1. If Bearer: EV-BearerToken then VJ-VerifyIdpToken. Else: VA-VerifyKey.
  2. AM-PrincipalFrom{Jwt,Key}: one uniform gw.principal
  3. EV-ReqModel + RF-ModelNotAllowed: model allow-list (403 if blocked)
  4. SA-SmoothBurst, QU-PerAppDaily, AM-SetTarget
▼  backend leg (key injected, hidden from user)
Apigee, target PreFlow
  1. KVM-GetAnthropicKey then AM-InjectBackendAuth (strip user credential)
▼
Claude backend, then response, then Apigee PostFlow
  1. EV-Usage, AM-Scrub, SC-Tokens, ML-Audit

Identity model: how "no Google login" works

OptionEnd-user holdsApigee verifies withStatus
A. Apigee API keyAPI key tied to an Apigee Developer AppVerifyAPIKeyWIRED
C. Customer-IdP JWTJWT from the customer's own Okta / Entra / Auth0EV-BearerToken + VerifyJWT (JWKS)WIRED
B. Apigee OAuth2short-lived token from Apigee's token endpointOAuthV2OPTIONAL
Both A and C are wired. The proxy does conditional auth: a request with Authorization: Bearer ... has its raw token extracted (EV-BearerToken, which strips the Bearer prefix) and verified as a customer-IdP JWT, otherwise the x-app-key API key is verified. Both resolve a single gw.principal, so quota, metering, and audit are identical regardless of auth method. The IdP issuer, JWKS, and audience come from resources/properties/idp.properties, so the same bundle points at any customer IdP by config, not code.

Secret handling (the crux): the Anthropic key lives once in an encrypted KVM, is injected only on the backend leg, and never appears in any user-visible response, header, or log. End-user credentials and the backend credential are fully decoupled.

Functional

  • FR1 Non-Google credential, then Apigee, then a valid Claude response.
  • FR2 Missing or invalid credential rejected at Apigee (401), backend never hit.
  • FR3 Anthropic key injected from secure storage, never user-visible.
  • FR4 Per-principal/tier quota, 429 on exceed.
  • FR5 Spike arrest protects backend.
  • FR6 Every call writes an audit record (identity, request id, model, tokens, status, time).
  • FR7 Token usage extracted and metered.
  • FR8 Faults return clean, governed errors.

Non-functional

  • NFR1 Security: no Google login in user path, secrets only encrypted, client credential never forwarded upstream.
  • NFR2 Observability: every allow/deny/quota/cost decision queryable.
  • NFR3 Portability: backend target is a config swap, not a rewrite.
  • NFR4 Repeatability: bundle deploys from repo via script, demo reproducible.
  • NFR5 Cost control: eval tier, low token caps, model allow-list, no surprise spend.

In scope (PoC)

  • One Apigee proxy fronting the Claude API.
  • Non-Google end-user authentication.
  • Backend Anthropic credential held in Apigee, injected on the backend leg.
  • Governance: verify, model allow-list, quota, spike arrest, audit, usage metering.
  • A demonstrable call path plus the audit record proving governance.

Out of scope (PoC)

  • Production multi-tenant hardening, HA, DR.
  • Billing/chargeback (usage captured, not invoiced).
  • A developer portal (Apigee provides one).
  • SSE streaming metering exactness (follow-up).
  • Claude content guardrails (this is a gateway PoC).

Acceptance / demo script

  • Valid non-Google credential, then 200 plus a real Claude answer.
  • Invalid or missing credential, then 401, backend never called.
  • Model not on the allow-list, then 403.
  • Quota exceeded, then 429.
  • Anthropic key absent from all user-visible output and logs.
  • Audit plus usage record visible in Apigee Analytics and the external sink.

Open questions

  • Cost attribution: per-app, per-end-user, or per-tier?
